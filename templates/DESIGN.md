# <项目名> 设计文档

> 这份文档要**先于代码存在**。AI 会读它来决定怎么实现 —— 没有它，AI 不会停下来问，
> 它会自己编一个设计然后照着做，而下一次会话会编一个不一样的。
>
> 写完后照 §8 把功能点逐条建成 issue 并挂里程碑。
> 写完删掉本段和所有 `<>` 占位说明。

## 1. 要解决什么问题

一段话。**从用户/使用者的角度写**，不要写技术方案。

如果这段写不出来，说明还不该建这个仓库。

## 2. 不做什么

明确列出**故意不做**的事，以及为什么。

这一节比第 1 节更有用：它是将来「要不要加这个功能」的判据，也是 AI 不会顺手多做一堆东西的唯一依据。

- 不做 X，因为……
- 暂不做 Y，等到……再考虑

## 3. 技术选型

org 默认值：后端 Rust、Web React、App Flutter、包管理 pnpm。
**只需要写偏离默认值的部分和理由。** 完全用默认值就写一句「全部采用 org 默认」。

| 层 | 选型 | 偏离默认的理由 |
|---|---|---|
| | | |

外部依赖（数据库、消息队列、第三方 API）也列在这里，每个写一句为什么需要它。

## 4. 部署

org 默认：**k8s + 私有 GHCR + 打 tag 触发构建与开 PR**（见工程规范 §5）。
这一节只写本项目要定的那几件事：

| 项 | 本项目 |
|---|---|
| 部署清单放哪 | `deploy/` 同仓库 / 独立 GitOps 仓库（二选一，选了就别混） |
| 环境有哪些 | dev / prod / … |
| 集群登记名 | 每个环境一条，dev 和 prod 是两条 |
| 镜像 | `ghcr.io/codelinkops/<仓库名>` |
| 副本数谁管 | HPA / 清单写死（HPA 管的话清单里不许写 `replicas`） |
| 有状态依赖 | 数据库、缓存、对象存储 —— 谁提供、怎么备份 |

**这个服务挂了会怎样？** 一句话写清影响面。这决定了它值不值得配告警、要不要多副本。

## 5. 数据模型

核心实体和它们的关系。不需要完整 DDL，但要说清：

- 有哪几张主要的表 / 集合
- 哪些字段是**不能改的**（外部引用、审计、幂等键）
- 哪些地方有唯一约束，为什么

## 6. 对外接口

API / CLI / 事件。列出主要端点和它们的鉴权要求。

**哪些是公开的、哪些必须登录、哪些需要更高权限** —— 这一栏要现在就想清楚，事后加鉴权总会漏掉某条路径。

## 7. 关键取舍

这一节写**将来的人会想问「为什么不那样做」的地方**。

每条写：做了什么选择、放弃了什么、为什么。

比如：「用轮询而不是 webhook，因为对端不保证送达，而漏一次的代价是……」

## 10. 待定

明确记下**还没想清楚的事**，不要假装都想好了。

一个诚实的「这里还没定，等看到实际数据再说」，比一个编出来的设计有用得多 —— 后者会被 AI 当成决定照着实现。
